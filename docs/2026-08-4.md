把write-stage的翻转值赋给read_stage（因为此时write-stage是写另一个buffer的目的地值，翻转后就是已经写好的buffer），然后根据read_stage的目的地进行矩阵计算
矩阵计算中k的for循环结束后，翻转write-stage，这时就指向刚刚算完的buffer了，然后开始下一轮循环
搬完最后一组数据，算完另一组buffer，这时tile_idx到顶了退出for循环，然后再额外写一块代码算完搬的最后一组数据

【懂分块矩阵计算的数学逻辑”不等于“写得出/调得通 GPU 上无 Bug 的物理坐标映射】
【1. 数学上的“优雅分块” vs 硬件上的“物理错位”
在数学上，写分块矩阵只是划几条虚线：
$$C_{i,j} = \sum A_{i,k} \cdot B_{k,j}$$
但在 GPU 硬件上，数据天生不是二维的，硬件更不认识你的“虚线”：
•	显存（Global Memory）是一根一维长线；
•	线程束（Warp）是以 32 为单位的一维平铺；
•	共享内存（Shared Memory）是有 32 个 Bank 的交叉物理阵列。
当你的 Tile 大小（比如 $64 \times 32$）、Block 线程排布（比如 $16 \times 16$） 和 数据搬运向量大小（比如 float4 / 128-bit） 三者数量对不上时，数学逻辑完全救不了你。
如果你不把坐标转换算术捋成本能反应，代码里一旦出现 tid / 32 写成 tid / 64 这种极其隐蔽的逻辑错位，GPU 不会报错，只会默默算出一堆垃圾值（或者偶尔随机报一个 Illegal Address Access 崩溃），让你排查三天三夜排查到怀疑人生。】

“如果我现在为了吃满 128-bit 带宽，把搬运改成了 float4，同时 Tile 变成 $128 \times 64$，但 Block 里我只给 256 个线程，请你在白板上写出这个线程搬运 $A$ 矩阵时的全局 Memory Offset 推导公式。”】

* 10.--block 线程 warp 矩阵分配 共享内存之间的关系
--Warp是最小数据传输单位，32线程一个【硬件指令发射与调度的最小单位】
--Block包含线程，可以自定义线程数量和组合形式（一维二维等）
--线程为最小任务单位。在这个版块里，一个线程掌握结果矩阵一个元素
--根据block大小（占用的线程数），寄存器情况和最大线程数情况，用grid明确能存在多少个block，完整地划分共享内存。
--而这个项目的双缓冲策略，是在block内实现的：把block分成两块，一块给线程们读取计算写入，另一块从gmem中读取数据，算完一块就交换过来继续一个读一个写
【物理上是按 Block 分配 Shared Memory；逻辑上是在 Block 专属的 Shared Memory 内部划分为 Stage 0 和 Stage 1 两个乒乓交替的缓冲区。】
--线程是一个指令流+寄存器上下文的概念，就相当于一个小推车：运输时32个一组（warp）去所属block的共享内存的一个stage中装数据，运到计算单元那，计算单元算好结果存储到线程的寄存器内，然后继续运继续存，任务结束得到真正结果后输出accum
